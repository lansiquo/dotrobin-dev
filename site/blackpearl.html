LAB WRITEUP · LINUX

Blackpearl

I investigated exposed web functionality and local privilege boundaries on Blackpearl, an isolated Linux training VM.

This writeup documents an isolated, offline training lab. Actual credentials and unrelated personal data are excluded.

Target environment

  • Target: Blackpearl
  • Operating system: Linux
  • Architecture: x86_64 (64-bit)
  • Service / application: Nginx 1.14.2; Navigate CMS 2.8
  • Weakness investigated: Navigate CMS remote code execution; owned by root SUID PHP interpreter
  • Scope: Intentionally vulnerable, isolated training VM

1. DNS enumeration and hostname resolution

I used DNSRecon to enumerate the target and identify blackpearl.tcm. I configured name resolution for blackpearl.tcm in /etc/hosts on Kali and my Mac.

I verified hostname resolution with getent and checked HTTP connectivity with curl. The server responded with HTTP 200 OK and identified itself as Nginx 1.14.2.

2. Web content discovery

I used FFUF with the medium DirBuster wordlist to discover exposed web content. Numerous requests returned identical 652-byte responses, so I filtered that response size to remove repeated baseline responses. A different response was a lead to inspect, not proof of a useful endpoint.

I identified /secret and discovered /navigate during further enumeration. The /navigate directory exposed Navigate CMS 2.8, which became my target for initial access.

3. Vulnerability research

I identified a Metasploit module for Navigate CMS 2.8 that chains authentication bypass with path traversal in the upload handler. Together, these weaknesses allow an unauthenticated attacker to place and execute PHP code remotely.

I selected the Navigate CMS RCE module, reviewed its options, and configured the target:

  • Target: Blackpearl (target)
  • Virtual host: blackpearl.tcm
  • Application path: /navigate/
  • Callback: Kali (attacker)

4. Initial access

I executed the exploit and obtained a shell through the vulnerable CMS. I ran whoami and confirmed that the session operated as www-data.

This established remote command execution under the web service account, but I still needed to identify a local privilege escalation path.

5. Shell stabilization and local enumeration

I used Python’s pty module to create a interactive terminal and make the Bash shell easier to use interactively.

I inspected my user identity, group memberships, sudo permissions, and shell history. These checks did not reveal a useful escalation path, so I continued with broader local enumeration.

6. LinPEAS enumeration

I hosted LinPEAS, a Linux privilege escalation enumeration script, from Kali using Python’s HTTP server on port 80, transferred the script to /tmp on Blackpearl, made it executable, and ran it.

I reviewed the results for privileged executables, writable paths, scheduled tasks, and configuration weaknesses. The enumeration identified PHP 7.3 as a potential privilege escalation vector.

7. SUID PHP investigation

I enumerated SUID (set user ID) binaries—executables that can run with their owner’s effective privileges—and inspected /usr/bin/php7.3. I identified the owned by root PHP interpreter as an executable that could run with elevated effective privileges.

I consulted GTFOBins and identified a technique using PHP’s pcntl_exec() function to launch a shell while retaining those privileges.

8. Privilege escalation

My initial command failed because of incorrect shell syntax. I corrected the quoting and executed:

/usr/bin/php7.3 -r 'pcntl_exec("/bin/sh", ["-p"]);'

This was a permissions problem, not a PHP vulnerability: a general purpose interpreter had been granted with root privileges execution. The command replaced the PHP process with /bin/sh. The -p option preserved the elevated effective privileges inherited from the SUID interpreter.

I ran whoami in the resulting shell and received root, confirming successful privilege escalation.

Result and evidence limits

Result: Root access achieved

I compromised Blackpearl by exploiting Navigate CMS 2.8, obtaining a www-data shell, and escalating privileges through a owned by root PHP interpreter with SUID (set user ID) permissions.

I completed the attack chain from web application exploitation to root access. The lab demonstrated how a vulnerable CMS and an unnecessarily privileged interpreter could be chained to compromise the entire host.

The selected captures show module configuration, the www-data shell, local commands, the PHP escalation and the final root identity. DNS/web enumeration results, the SUID permission listing and full LinPEAS findings are described in the notes but are not present in the selected screenshots. Recommended fixes were not retested.

Attack path

  2. Web content discovery
  3. Navigate CMS code execution
  4. www-data

  7. Root

9. Findings and remediation

Recommended actions, not completed fixes. No remediation retest is claimed.

Attack / finding

Navigate CMS remote code execution

I exploited the vulnerable CMS to execute commands as www-data. This exposed the application’s files and resources accessible to its service account and provided a foothold for further compromise.

Recommended defensive action

Recommended fixes include upgrading or replacing the vulnerable CMS, restricting unnecessary application functionality, and limiting service account permissions.

Attack / finding

SUID PHP privilege escalation

I used the privileged PHP interpreter to escalate from www-data to a with root privileges shell. Combined with the CMS vulnerability, this enabled full host compromise.

Recommended defensive action

Recommended fixes include removing unnecessary SUID permissions from interpreter binaries, auditing privileged executable ownership and permissions, and enforcing least privilege.
