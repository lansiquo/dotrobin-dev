LAB WRITE-UP · LINUX

Dev

I investigated how an exposed NFS archive and a permissive sudo rule connected file access to privileged command execution on Dev.

An isolated offline training lab. Passwords, credential hashes and private keys are excluded.

On this page ⌄

Target environment

  • Target: Dev
  • Operating system: Linux; distribution not recorded in the selected evidence
  • Architecture: Not recorded
  • Service / application: NFS and SSH; local ZIP utility
  • Weakness investigated: Exposed encrypted archive containing a private key and unrestricted sudo ZIP execution
  • Scope: Intentionally vulnerable, isolated training VM

Attacker: Kali Linux. Captured addresses remain in commands and evidence; passwords, hashes and private key material are excluded.

1. Enumerate and mount the NFS export

I enumerated Dev’s NFS exports and found /srv/nfs. NFS provides remote filesystem access; the captured export listing shows it was available to broad private network ranges.

showmount -e 192.168.18.8

I mounted the export on Kali and inspected its contents. These commands are recorded in my reporting page.

sudo mkdir -p /mnt/dev
sudo mount -t nfs 192.168.18.8:/srv/nfs /mnt/dev
ls -la /mnt/dev

2. Recover the encrypted archive

The share contained save.zip. I used an offline wordlist attack against the archive, then extracted it. The retained extraction capture confirms id_rsa and todo.txt; the separate cracking capture contains the recovered password and is excluded.

fcrackzip -v -u -D \
  -p /usr/share/wordlists/rockyou.txt \
  save.zip
unzip save.zip

Recovering an archive password exposed authentication material stored inside it. Archive encryption did not compensate for placing a reusable private key on an accessible share.

3. Establish the local account context

My reporting page describes authenticating with the recovered SSH key after ordinary password authentication failed. It records the following command template; user is a placeholder, not a verified account name.

chmod 600 id_rsa
ssh -i id_rsa user@192.168.18.8

A retained earlier SSH attempt as jp failed. Later terminal captures show a shell as jeanpaul on Dev, but the exact successful SSH invocation is not retained in the selected evidence. I do not substitute a guessed command or reproduce the private key.

4. Inspect the sudo boundary

I checked which commands the local account could run with elevated privileges. The capture shows permission to run ZIP as root without a password.

sudo -l

ZIP’s archive testing option accepts an external command. Allowing unrestricted privileged execution of this utility also grants access to that command execution feature.

5. Invoke ZIP’s external test command

I created a temporary archive and supplied a shell as its external test command. The captured invocation matches the reporting page:

sudo zip /tmp/shell.zip /etc/hosts -T -TT '/bin/sh #'

-T tests the archive; -TT selects the test command. Because sudo runs ZIP as root, the spawned shell inherits that privilege. The trailing comment marker prevents the appended archive argument from becoming part of the intended shell invocation. See the GTFOBins ZIP reference for the utility behavior.

Result and evidence limits

The retained capture shows whoami returning root and hostname returning dev, immediately after the sudo ZIP command.

whoami
hostname

Root access and the sudo ZIP mechanism are directly captured. The successful SSH login command is missing; the reporting page provides a generic template and a later local account shell establishes the subsequent context. Its id output is labeled expected, so I do not present it as captured evidence. Credential-bearing cracking and private-key captures remain excluded. No remediation retest is claimed.

  2. Encrypted archive

6. Findings and remediation

Recommended actions, not completed fixes. No remediation retest is claimed.

Attack / finding

Exposed NFS archive

A reachable export disclosed an encrypted archive holding authentication material.

Recommended defensive action

Restrict exports to required clients and identities, remove secrets from shares and review filesystem permissions.

Attack / finding

Recoverable credentials

An offline wordlist attack recovered the archive password, exposing a private key.

Recommended defensive action

Revoke and replace the exposed key, remove its copies, use appropriate secret storage and avoid relying on archive passwords as an access boundary.

Attack / finding

Privileged utility execution

The sudo rule allowed ZIP’s external command feature to launch a root shell.

Recommended defensive action

Remove unrestricted sudo access to ZIP. Replace it with a narrowly scoped operation that cannot select arbitrary commands, and validate the resulting permissions.
