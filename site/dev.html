Overview

  • Target: Dev
  • OS: Debian Linux, kernel 4.19.0-16-amd64, x86_64
  • Service: NFS, SSH, Bolt on port 80, BoltWire on port 8080; local ZIP utility
  • Attack: Open NFS export, cracked archive, BoltWire file inclusion for the username, SSH private key, sudo ZIP to root
  • Scope: Intentionally vulnerable, isolated training VM

I pulled an encrypted archive off an open NFS export, cracked it for an SSH private key, found the username jeanpaul through a BoltWire file inclusion, logged in with the key and used a sudo rule on ZIP to become root.

Reconnaissance

Placeholders in angle brackets, such as <TARGET_IP>, stand in for lab values. Nmap showed NFS on TCP/2049:

2049/tcp open  nfs  3-4 (RPC #100003)

The export listing showed /srv/nfs open to broad private network ranges, so I checked what it held.

showmount -e <TARGET_IP>

I mounted the export on Kali and inspected its contents:

sudo mkdir -p /mnt/dev
sudo mount -t nfs <TARGET_IP>:/srv/nfs /mnt/dev
ls -la /mnt/dev

The web ports had more. Port 80 showed a Bolt installation error, and /app/cache/config-cache.json was readable, exposing Bolt’s database settings. Port 8080 showed a PHP info page, and /dev/ on that port ran BoltWire.

Initial access

The share held save.zip. I ran an offline wordlist attack against it, recovered the password and extracted id_rsa and todo.txt:

fcrackzip -v -u -D \
  -p /usr/share/wordlists/rockyou.txt \
  save.zip
unzip save.zip

The archive password opened only the archive, not SSH. The private key inside was the way in, and encrypting the archive did not protect a key left on an open share.

todo.txt was signed jp, so I tried the key as jp. SSH asked for a password and denied me:

ssh -i id_rsa jp@<TARGET_IP>
jp@<TARGET_IP>'s password:
Permission denied, please try again.

To find the username, I used a known BoltWire 6.03 local file inclusion (Exploit-DB 48411). Logged in to BoltWire, I requested /etc/passwd through the search action:

http://<TARGET_IP>:8080/dev/index.php?p=action.search&action=../../../../../../../etc/passwd
jeanpaul:x:1000:1000:jeanpaul,,,:/home/jeanpaul:/bin/bash

Then I logged in with the key:

chmod 600 id_rsa
ssh -i id_rsa <USER>@<TARGET_IP>

That gave me a shell as jeanpaul on Dev.

Privilege escalation

I checked the account’s sudo rights: it could run ZIP as root without a password.

sudo -l

ZIP’s archive test option accepts an external command, so unrestricted sudo access to ZIP is root command execution. I created a temporary archive and supplied a shell as its test command:

sudo zip /tmp/shell.zip /etc/hosts -T -TT '/bin/sh #'

-T tests the archive and -TT sets the test command. Because sudo runs ZIP as root, the shell runs as root; the trailing # keeps the appended archive argument out of the shell command. See the GTFOBins ZIP reference.

Result

Result: Root access achieved

Right after the sudo ZIP command, whoami returned root and hostname returned dev.

whoami
hostname

Attack path

  1. NFS export
  2. Encrypted archive
  3. Offline password recovery
  4. BoltWire file inclusion reveals jeanpaul
  5. SSH login with the private key
  6. Local shell as jeanpaul
  7. Sudo ZIP external command
  8. Root

Remediation

Finding

Exposed NFS archive

A reachable export disclosed an encrypted archive holding authentication material.

Fix

Restrict exports to required clients and identities, remove secrets from shares and review filesystem permissions.

Finding

Recoverable credentials

An offline wordlist attack recovered the archive password and exposed a private key.

Fix

Revoke and replace the exposed key, remove its copies, use proper secret storage and stop relying on archive passwords as an access boundary.

Finding

Web file inclusion and exposed configuration

BoltWire let a logged-in user read /etc/passwd through path traversal, and Bolt’s config cache was readable on port 80.

Fix

Update or remove BoltWire, serve Bolt from its public/ folder so configuration and cache files stay outside the web root, and take development apps off exposed hosts.

Finding

Privileged utility execution

The sudo rule let ZIP’s external command feature launch a root shell.

Fix

Remove unrestricted sudo access to ZIP. If privileged archiving is needed, allow only a narrow operation that cannot choose arbitrary commands or privileged paths. Audit other sudo rules for the same problem.

Key takeaways

  • Encrypting the archive did not protect the key: the share was open and a wordlist recovered the password.
  • Unrestricted sudo on ZIP gave me a root shell through -TT; any sudo rule on a tool that can run commands needs the same scrutiny.
  • NFS exports should list only the clients that need them.
