Overview

  • Target: Dev
  • OS: Linux, x86_64
  • Service: NFS and SSH; local ZIP utility
  • Attack: Open NFS export, cracked archive, SSH private key, sudo ZIP to root
  • Scope: Intentionally vulnerable, isolated training VM

I pulled an encrypted archive off an open NFS export, cracked it for an SSH private key, got a shell as jeanpaul and used a sudo rule on ZIP to become root.

Reconnaissance

Placeholders in angle brackets, such as <TARGET_IP>, stand in for lab values. The export listing showed /srv/nfs open to broad private network ranges, so I checked what it held.

showmount -e <TARGET_IP>

I mounted the export on Kali and inspected its contents:

sudo mkdir -p /mnt/dev
sudo mount -t nfs <TARGET_IP>:/srv/nfs /mnt/dev
ls -la /mnt/dev

Initial access

The share held save.zip. I ran an offline wordlist attack against it, recovered the password and extracted id_rsa and todo.txt:

fcrackzip -v -u -D \
  -p /usr/share/wordlists/rockyou.txt \
  save.zip
unzip save.zip

The archive password only unlocked the archive, not SSH; the private key inside was a separate way in. Archive encryption did not make up for leaving reusable authentication material on an accessible share.

Password login over SSH failed, so I used the key:

chmod 600 id_rsa
ssh -i id_rsa <USER>@<TARGET_IP>

That gave me a shell as jeanpaul on Dev.

Privilege escalation

I checked the account’s sudo rights: it could run ZIP as root without a password.

sudo -l

ZIP’s archive test option accepts an external command, so unrestricted sudo access to ZIP is root command execution. I created a temporary archive and supplied a shell as its test command:

sudo zip /tmp/shell.zip /etc/hosts -T -TT '/bin/sh #'

-T tests the archive and -TT sets the test command. Because sudo runs ZIP as root, the shell runs as root; the trailing # keeps the appended archive argument out of the shell command. See the GTFOBins ZIP reference.

Result

Result: Root access achieved

Right after the sudo ZIP command, whoami returned root and hostname returned dev.

whoami
hostname

Attack path

  1. NFS export
  2. Encrypted archive
  3. Offline password recovery
  4. SSH login with the private key
  5. Local shell as jeanpaul
  6. Sudo ZIP external command
  7. Root

Remediation

Finding

Exposed NFS archive

A reachable export disclosed an encrypted archive holding authentication material.

Fix

Restrict exports to required clients and identities, remove secrets from shares and review filesystem permissions.

Finding

Recoverable credentials

An offline wordlist attack recovered the archive password and exposed a private key.

Fix

Revoke and replace the exposed key, remove its copies, use proper secret storage and stop relying on archive passwords as an access boundary.

Finding

Privileged utility execution

The sudo rule let ZIP’s external command feature launch a root shell.

Fix

Remove unrestricted sudo access to ZIP. If privileged archiving is needed, allow only a narrow operation that cannot choose arbitrary commands or privileged paths. Audit other sudo rules for the same problem.

Key takeaways

  • An encrypted archive does not protect a private key left on an open share.
  • A sudo rule on any tool that can run commands, like ZIP’s -TT, is a root shell; GTFOBins is the first place I check.
  • NFS exports should list only the clients that need them.
