PROJECT

sast-triage

I built a GitHub pull request security reviewer: a Python service that scans the changed Python files with Semgrep and posts each finding as an annotation on the exact file and line. Semgrep performs static analysis, so the submitted code is never run.

Technologies & stack

The application is a Python webhook service. The portfolio demo is a separate static walkthrough.

  • Language & API: Python 3.11–3.13, FastAPI and Uvicorn; Pydantic for the API framework's data layer.
  • Security analysis: Semgrep with service-owned Python rules, subprocess execution and JSON findings mapped to GitHub Check Run annotations.
  • GitHub integration & authentication: GitHub App webhooks and REST API; HMAC-SHA256 signature validation; Requests and certifi for HTTPS; PyJWT and cryptography for App authentication; python-dotenv for local configuration.
  • Tests & developer workflow: pytest, HTTPX, pip, Python virtual environments, Make and GitHub Actions, which runs the suite on every pull request. The local interactive showcase uses FastAPI with HTML, CSS and JavaScript.
  • Prepared deployment, not live: SQLite job queue, a separate Python worker, Linux and rootless Docker scanner isolation. Deployment and real isolation acceptance remain pending.
  • This website & browser demo: HTML, CSS, vanilla JavaScript and JSON fixtures, hosted on GitHub Pages. No FastAPI backend, Python runtime or Semgrep scanner runs in this public demo.

Source: application dependencies · deployment scope.

The problem

A review needs more than a red or green badge: it needs a location, a reason and an honest statement of coverage. I designed the pipeline so scanner failures cannot become reassuring passes, and files from the repository cannot redefine the scanner’s rules.

Input → scan → output

  1. Authenticate the request. Verify the webhook’s HMAC-SHA256 signature—a shared secret check over the exact request body—then validate the repository and commit identifiers.
  2. Prepare the exact revision. Download a bounded archive of the pull request’s head commit, reject unsafe archive entries and stage only changed Python files. The scan covers each selected file, not just added lines.
  3. Run the service’s own rules. Analyze the staged source with Semgrep. Pull request configuration, ignore files and inline suppression comments cannot disable the production rules.
  4. Return reviewable findings. Convert findings into GitHub Check Run annotations: messages attached to specific files and lines on the reviewed commit. Cap output at 200 annotations, sent in batches of 50.

Outcome handling: findings or scanner/incomplete scan errors produce failure. Deleted-only and unsupported-language changes are neutral. A clean result means the selected rules found nothing in the scanned Python files—not that the repository is secure.

Security controls and their limits

My implementation treats the webhook sender, repository author and scanner as separate trust boundaries: each can supply input the next component must validate.

  • Untrusted archives: reject path traversal, links, duplicate entries and excessive size/member counts before staging source.
  • Untrusted source: never execute repository code, install hooks or tests. Keep application credentials out of the scanner subprocess environment.
  • Scanner failures: reject malformed output and incomplete scans rather than reporting success.

These controls reduce exposure; staging files and removing credentials do not create an operating system sandbox. The default demo uses local subprocesses and in-memory jobs. The separately prepared deployment mode uses a SQLite-backed queue and a dedicated worker with a rootless container design. Its actual Linux isolation still needs verification.

What has been verified

Test and rule counts re-checked on 5 November 2026 against the GitHub main branch, at v1.0.0. The dependency and acceptance items are recorded checkpoints from 29 October 2026.

242 local tests
The offline suite passes locally and in GitHub Actions on every pull request. GitHub and Docker integration calls in that suite are mocked; local database and recovery behavior are exercised.
15 production rules
Local scanner compatibility checks passed, including suppression resistance and a clean comparison.
5 dependency advisories
Unresolved in the tested Semgrep 1.182.1 environment. A container boundary does not patch vulnerable dependencies.
Acceptance still pending
Final Linux image audit, real rootless container boundaries and authenticated GitHub delivery, exact commit reporting and recovery checks.

Scope: selected Python security patterns only. No dependency, secret, JavaScript or infrastructure scanning. Findings are ranked P1–P3 and labelled new or pre-existing, but a person still reviews them; the rules can miss vulnerabilities or report false positives.

Run it yourself

The reviewer is in active development on GitHub. Setup uses Python 3.11–3.13. The demo environment has known dependency findings, so use it with the bundled trusted fixtures only, not for public repositories or production.

git clone https://github.com/lansiquo/Pull-Request-Reviewer.git
cd Pull-Request-Reviewer
python3 -m venv .venv
source .venv/bin/activate
python -m pip install -r requirements.txt
make check

make test runs the offline regression suite with outbound HTTP blocked. make demo scans two bundled source fixtures without executing them and prints annotation JSON. make check runs both.

The demo finds two high-severity issues in the vulnerable fixture (MD5 and shell execution) and none in the clean one. I re-ran it on 4 November 2026 with those results.

For the full interactive version, run .venv/bin/python demo_web.py and open http://127.0.0.1:8765. It’s the local counterpart of the browser demo: pick an example, run the check, apply the fix and run it again. Four examples run real Semgrep scans with a small demo ruleset; six run real behavioral tests that execute authored, hash-pinned fixtures in isolated child processes against synthetic services. The pull request view is simulated, and only bundled fixtures are accepted.
