FEATURED PROJECT

Pull Request Reviewer

I built a Python-focused pull-request review pipeline that turns Semgrep findings into file-and-line annotations. Semgrep performs static analysis: it inspects source patterns without running the submitted code.

Local prototype; not a live scanning service. This portfolio does not accept repository uploads or run scans. Deployment preparation exists, but production acceptance is incomplete.

The problem

A review needs more than a red or green badge: it needs a location, a reason and an honest statement of coverage. I designed the pipeline so scanner failures cannot become reassuring passes, and repository-controlled files cannot redefine the scanner’s rules.

Input → scan → output

  1. Authenticate the request. Verify the webhook’s HMAC-SHA256 signature—a shared-secret check over the exact request body—then validate the repository and commit identifiers.
  2. Prepare the exact revision. Download a bounded archive of the pull request’s head commit, reject unsafe archive entries and stage only changed Python files. The scan covers each selected file, not just added lines.
  3. Run service-owned rules. Analyze the staged source with Semgrep. Pull-request configuration, ignore files and inline suppression comments cannot disable the production rules.
  4. Return reviewable findings. Convert findings into GitHub Check Run annotations: messages attached to specific files and lines on the reviewed commit. Cap output at 200 annotations, sent in batches of 50.

Outcome handling: findings or scanner/partial-scan errors produce failure. Deleted-only and unsupported-language changes are neutral. A clean result means the selected rules found nothing in the scanned Python files—not that the repository is secure.

Security controls and their limits

My implementation treats the webhook sender, repository author and scanner as separate trust boundaries: each can supply input the next component must validate.

  • Untrusted archives: reject path traversal, links, duplicate entries and excessive size/member counts before staging source.
  • Untrusted source: never execute repository code, install hooks or tests. Keep application credentials out of the scanner subprocess environment.
  • Scanner failures: reject malformed output and incomplete scans rather than reporting success.

These controls reduce exposure; staging files and removing credentials do not create an operating-system sandbox. The default demo uses local subprocesses and in-memory jobs. The separately prepared deployment mode uses a SQLite-backed queue and a dedicated worker with a rootless container design. Its actual Linux isolation still needs verification.

Reproduce the local demo

In an existing project checkout, the documented setup uses Python 3.11–3.13. The original demo environment has known dependency findings; it is for trusted local fixtures, not public repository intake or production deployment.

python3 -m venv .venv
source .venv/bin/activate
python -m pip install -r requirements.txt
make check

make test runs the offline regression suite with outbound HTTP blocked. make demo scans two bundled source fixtures without executing them and prints annotation JSON. make check runs both.

The documented demo expects two high-severity findings in the vulnerable fixture (MD5 and shell execution), and zero in the clean fixture. The pull-request presentation is simulated; the local fixture scans are real. No live GitHub outcome is claimed by the demo.
