FIELD NOTES / ISOLATED TRAINING LAB

Blue
Verify the identity.

This investigation concerns an intentionally vulnerable, isolated training VM. The account identities below are lab identities. Public notes omit passwords, hashes, callback addresses, and unrelated local data.

Blue is an isolated Windows 7 SP1 x64 lab centered on SMB and EternalBlue. Its strongest lesson is simple: a vulnerability check, a session opening, and an identity check are different pieces of evidence.

01 / Start with the exposed service

The notes focus on SMB on TCP/445. The reporting draft describes Nmap and Metasploit checks for MS17-010, but labels their output as expected. Those examples are methodology, not raw captured results. The saved terminal screenshots provide the firmer evidence for the exploitation and verification stages.

02 / Match the architecture and session

The preserved configuration screenshot selects exploit/windows/smb/ms17_010_eternalblue and an x64 Windows Meterpreter reverse-TCP payload. The actual screenshot uses callback port 4444; the reporting draft later gives 2222 as a setup example. The public account follows the captured session rather than treating those values as interchangeable history.

03 / Confirm what the session can do

The terminal capture records the exploit’s overwrite-success message and a Meterpreter session opening. A direct whoami attempt at the Meterpreter prompt returned “Unknown command.” Switching to Meterpreter’s getuid established the security context:

meterpreter > getuid
Server username: NT AUTHORITY\SYSTEM

meterpreter > sysinfo
OS: Windows 7 (6.1 Build 7601, Service Pack 1).
Architecture: x64
Meterpreter: x64/windows

This is selected text transcribed from the retained screenshot; local addresses and machine name are omitted. The evidence supports SYSTEM-level execution in that session. A separate local privilege-escalation stage was not needed for this recorded path.

04 / Account for operational impact

The original notes also record a crashed machine. A successful exploit does not mean a stable target. That is a practical reason to use isolated disposable labs and to preserve verification evidence before drawing conclusions.

Defensive lessons

  • Replace unsupported operating systems and apply the applicable SMB security fixes.
  • Disable SMBv1 where it is not required and restrict SMB reachability.
  • Separate vulnerability indicators from verified execution and identity evidence.
  • Retest the exposed service and monitor for service instability after changes.

Evidence and limitations

The original terminal screenshots confirm the selected module, x64 payload, opened session, and SYSTEM identity. The report’s example scan output is not presented as observed. No production target, persistence, or remediation retest is claimed.
