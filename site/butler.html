Butler

Overview

  • Target: Butler
  • OS: Windows 10, x64
  • Service: Jenkins on TCP/8080
  • Attack: Jenkins access to command execution, WinPEAS enumeration, SYSTEM shell
  • Scope: Intentionally vulnerable, isolated training VM

I found Jenkins on Butler, used it to run commands on Windows, mapped the host with WinPEAS and finished with a shell as NT AUTHORITY\SYSTEM.

Reconnaissance

Placeholders such as <TARGET_IP> stand in for lab addresses. I scanned the target’s service ports:

sudo nmap -sS -sV -Pn -n -p 22,80,8080 <TARGET_IP>

Jenkins, an automation server that can run build tasks, was on TCP/8080.

Initial access

I attacked the Jenkins login at /j_spring_security_check with Burp Suite Intruder, using the usernames admin, administrator and jenkins. Through Jenkins I reached command execution on Windows. Jenkins ran as BUTLER\butler from C:\Program Files\Jenkins.

Privilege escalation

I ran WinPEAS to map the local context:

winpeas.exe

It showed BUTLER\butler at high integrity, with administrator membership enabled, SeImpersonatePrivilege, SeDebugPrivilege and UAC disabled. It also flagged Print Spooler issues and service permissions.

WinPEAS also flagged WiseBootAssistant, which ran automatically as LocalSystem from this unquoted path:

C:\Program Files (x86)\Wise\Wise Care 365\BootTime.exe

I queried the service and restarted it:

sc.exe qc WiseBootAssistant
sc.exe query WiseBootAssistant
sc.exe stop WiseBootAssistant
sc.exe start WiseBootAssistant
sc.exe queryex WiseBootAssistant

The first start returned error 1053.

Result

Result: SYSTEM access achieved

I reached NT AUTHORITY\SYSTEM, Windows’ built-in LocalSystem identity, on the Windows 10 lab VM. My Kali listener on TCP/7777 caught the callback from Butler:

# Kali listener
nc -lvnp 7777
listening on [any] 7777 ...
connect to [<CALLBACK_IP>] from (UNKNOWN) [<TARGET_IP>] 52614
Microsoft Windows [Version 10.0.19043.928]

C:\Windows\system32>whoami
nt authority\system

Attack path

  1. Jenkins on TCP/8080
  2. Burp Suite Intruder against the Jenkins login
  3. Command execution as BUTLER\butler
  4. WinPEAS enumeration
  5. SYSTEM shell on TCP/7777

Remediation

Finding

Jenkins access

Jenkins was reachable on TCP/8080, and access to it gave me command execution on Windows.

Fix

Harden authentication and restrict build and script execution to authorized operators.

Finding

Privileged service context

Jenkins ran at high integrity, with administrator membership enabled and UAC disabled.

Fix

Reduce build account privileges, remove unnecessary administrative membership and turn UAC back on.

Finding

Unquoted service path

WinPEAS flagged WiseBootAssistant running automatically as LocalSystem from an unquoted path with spaces.

Fix

Quote the service executable path, restrict write access to every folder on it, audit service-control rights and use the least-privileged service account that works.

Key takeaways

  • A build server that runs commands is a remote shell for anyone who gets past its login.
  • Service accounts for CI tools should never hold administrator rights; this one also had UAC off.
  • WinPEAS surfaces unquoted service paths fast; I check each one for quotes and writable folders.
