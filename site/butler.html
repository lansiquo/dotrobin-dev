FIELD NOTES / ISOLATED TRAINING LAB

Butler
Prove the outcome.

This investigation concerns an intentionally vulnerable, isolated training VM. The account identities below are lab identities. Public notes omit passwords, hashes, callback addresses, and unrelated local data.

Butler combines Jenkins access, Windows enumeration, and service configuration investigation. The retained evidence confirms a SYSTEM shell. It also illustrates why the final identity alone cannot prove the exact mechanism that produced it.

01 / From Jenkins to a Windows context

The source report identifies Jenkins on TCP/8080 and describes testing login combinations through Burp Suite Intruder. Credentials are omitted here. A redirect was a signal to investigate, not proof of successful authentication by itself.

The subsequent enumeration records the Jenkins service account as BUTLER\butler. The exact Jenkins command used to establish initial execution was not retained, so this write-up does not supply a fabricated command.

02 / Investigate a privileged service

WinPEAS identified WiseBootAssistant as a LocalSystem service with an unquoted executable path:

C:\Program Files (x86)\Wise\Wise Care 365\BootTime.exe

An unquoted path containing spaces creates ambiguous executable resolution. Exploitability also depends on permissions on candidate locations and the ability to trigger execution. The path alone is not proof of a successful privilege-escalation exploit.

The report records checking the service configuration and state, then testing stop/start behavior. An early attempt returned service error 1053. That error described a service startup problem; it did not, on its own, establish whether a payload had run.

03 / Verify the resulting identity

A later retained terminal screenshot shows a callback from the Butler VM and a native Windows shell. The identity check is explicit:

C:\Windows\system32>whoami
nt authority\system

This confirms SYSTEM execution. It supersedes the earlier investigation diagram that labelled the shell unconfirmed. However, the screenshot does not establish which executable launched, where it was placed, or the exact trigger. Attribution to unquoted-path abuse remains incomplete.

Defensive lessons

  • Harden Jenkins authentication and restrict access to build and script execution.
  • Give build services only the privileges required for their tasks.
  • Quote service executable paths and audit write access along those paths.
  • Review service configuration-change rights and retain process creation evidence to validate the mechanism.

Evidence and limitations

Based on the original Butler report, WinPEAS notes, and the later terminal screenshot showing SYSTEM. The initial command, payload placement, and full service-trigger chain are not preserved. No claim is made that every stage of the suspected exploit mechanism has been proven or that remediation was retested.
