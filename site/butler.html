Butler

I examined Jenkins access and local privilege boundaries on Butler, an isolated Windows 10 training VM.

On this page ⌄

Target environment

  • Target: Butler
  • Operating system: Windows 10
  • Architecture: x64 (64-bit)
  • Service / application: Jenkins on TCP/8080
  • Weakness investigated: WiseBootAssistant unquoted service path; exact escalation trigger not retained
  • Scope: Intentionally vulnerable, isolated training VM

1. Locate Jenkins and establish access

My notes include this reconstructed scan; it is not saved scanner output.

Placeholders such as <TARGET_IP> stand in for lab addresses.

Reconstructed command

sudo nmap -sS -sV -Pn -n -p 22,80,8080 <TARGET_IP>

Jenkins, an automation server that can run build tasks, was on TCP/8080. My notes describe using Burp Suite Intruder against /j_spring_security_check with the usernames admin, administrator and jenkins. A 302 redirect alone did not prove a login; the later workflow did reach Windows execution. Tested passwords are omitted and the initial shell command was not recorded. Jenkins itself ran as BUTLER\butler from C:\Program Files\Jenkins.

2. Enumerate the execution context

Documented command

winpeas.exe

I ran WinPEAS to inspect the local context. The retained notes identify BUTLER\butler, high integrity, enabled administrator membership, SeImpersonatePrivilege, SeDebugPrivilege and disabled UAC: context and candidate paths, not proof that a specific privilege was exploited.

WinPEAS also flagged potential Print Spooler vulnerabilities and service permissions. The walkthrough next investigates WiseBootAssistant, a candidate mechanism rather than an established cause of the later SYSTEM callback. It ran automatically as LocalSystem with this unquoted path:

Documented command

C:\Program Files (x86)\Wise\Wise Care 365\BootTime.exe

3. Inspect and test the service

I inspected and restarted the service:

Documented command

sc.exe qc WiseBootAssistant
sc.exe query WiseBootAssistant
sc.exe stop WiseBootAssistant
sc.exe start WiseBootAssistant
sc.exe queryex WiseBootAssistant

An unquoted path with spaces makes executable resolution ambiguous; exploiting it also needs a writable candidate location and a trigger. The service first returned error 1053 (recorded in my notes, not captured), which neither proves nor disproves payload execution.

4. Confirm SYSTEM

My later screenshot shows a callback from Butler to a Kali listener on TCP/7777:

Documented command

# Kali listener
nc -lvnp 7777
listening on [any] 7777 ...
connect to [<CALLBACK_IP>] from (UNKNOWN) [<TARGET_IP>] 52614
Microsoft Windows [Version 10.0.19043.928]

C:\Windows\system32>whoami
nt authority\system

That shows SYSTEM, but not which executable launched, where it was placed or what triggered it, so it does not prove an unquoted-path exploit. The preceding account is documented as high-integrity with administrator membership, so it also does not establish a crossing from a low-privilege account.

5. Result and evidence limits

Result: SYSTEM access achieved

I reached NT AUTHORITY\SYSTEM execution (Windows’ built in LocalSystem identity) on the Windows 10 lab VM. The initial Jenkins command, payload placement and exact escalation trigger were not retained, so no full unquoted path exploit chain or remediation retest is claimed.

6. Attack path

  1. Jenkins discovery and documented credential testing
  2. Documented Windows execution; initial command not retained
  3. WinPEAS context and service enumeration
  4. WiseBootAssistant investigated as a candidate mechanism
  5. Later captured SYSTEM shell; causal trigger not retained

7. Findings and remediation

Attack / finding

Jenkins access

Jenkins discovery and Windows execution are recorded; the original initial shell command is not retained.

Recommended defensive action

Harden authentication and restrict build/script execution to authorized operators.

Attack / finding

Privileged service context

The notes describe high integrity, administrative membership and disabled UAC.

Recommended defensive action

Reduce build account privileges; review unnecessary administrative membership and disabled UAC.

Attack / finding

Unquoted service path

WiseBootAssistant was investigated, but the retained evidence does not establish that this path caused the SYSTEM shell.

Recommended defensive action

Quote the service executable path, restrict write access to candidate executable locations, audit service-control rights and use the least-privileged service account that works. No remediation retest was performed.
