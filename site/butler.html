Butler

I examined Jenkins access and local privilege boundaries on Butler, an isolated Windows 10 training VM.

On this page ⌄
Target environment1. Locate Jenkins and establish access2. Enumerate the execution context3. Inspect and test the service4. Confirm SYSTEM5. Result and evidence limits6. Attack path7. Findings and remediation

Target environment

  • Target: Butler
  • Operating system: Windows 10
  • Architecture: x64 (64-bit)
  • Service / application: Jenkins on TCP/8080
  • Weakness investigated: WiseBootAssistant unquoted service path; exact escalation trigger not retained
  • Scope: Intentionally vulnerable, isolated training VM

1. Locate Jenkins and establish access

My notes include this reconstructed scan sequence for the services investigated in the lab; it is not saved scanner output:

sudo nmap -sS -sV -Pn -n -p 22,80,8080 192.168.18.9

Jenkins, an automation server capable of running build tasks, was accessible on TCP/8080. My notes describe using Burp Suite Intruder to test login combinations against /j_spring_security_check, cycling the usernames admin, administrator and jenkins. HTTP 302 redirects alone did not prove authentication; the subsequent workflow reached Windows execution. Tested passwords and the unrecorded initial shell command are omitted. My notes record that the Jenkins service itself ran as BUTLER\butler from C:\Program Files\Jenkins.

2. Enumerate the execution context

winpeas.exe

I used WinPEAS, a Windows privilege escalation enumeration tool, to inspect the local context. The retained notes identify BUTLER\butler, high integrity, enabled administrator membership, SeImpersonatePrivilege and SeDebugPrivilege, and disabled UAC. These are context and candidate attack paths, not proof that a specific privilege was exploited.

WinPEAS also flagged potential Windows Print Spooler vulnerabilities and several service permissions worth examining. Of these, the WiseBootAssistant service was the path I pursued.

WiseBootAssistant ran automatically as LocalSystem with this unquoted executable path:

C:\Program Files (x86)\Wise\Wise Care 365\BootTime.exe

3. Inspect and test the service

My service investigation used:

sc.exe qc WiseBootAssistant
sc.exe query WiseBootAssistant
sc.exe stop WiseBootAssistant
sc.exe start WiseBootAssistant
sc.exe queryex WiseBootAssistant

An unquoted path with spaces creates ambiguous executable resolution; exploitation also requires writable candidate locations and a way to trigger execution. The service initially returned error 1053. That startup error alone neither proves nor disproves payload execution.

4. Confirm SYSTEM

My later saved screenshot shows a callback from the Butler VM to a Kali listener on TCP/7777:

# Kali listener
nc -lvnp 7777
listening on [any] 7777 ...
connect to [192.168.18.4] from (UNKNOWN) [192.168.18.9] 52614
Microsoft Windows [Version 10.0.19043.928]

C:\Windows\system32>whoami
nt authority\system

This confirms SYSTEM execution. It does not identify the executable that launched, its placement, or the triggering command.

5. Result and evidence limits

Result: SYSTEM access achieved

I reached NT AUTHORITY\SYSTEM execution (Windows’ built in LocalSystem identity) on the Windows 10 lab VM. My notes trace Jenkins access into local enumeration and a suspicious privileged service. The final identity is captured; the exact command that caused the escalation was not retained.

Jenkins discovery, WinPEAS findings, the service misconfiguration, callback, and SYSTEM identity are documented. The initial Jenkins command, payload placement, and exact escalation trigger are not. No full unquoted path exploit chain or remediation retest is claimed.

6. Attack path

  1. Jenkins discovery
  2. credential testing
  3. Windows execution
  4. WinPEAS
  5. WiseBootAssistant investigation
  6. SYSTEM shell

7. Findings and remediation

Attack / finding

Jenkins access

Jenkins discovery and Windows execution are recorded; the original initial shell command is not retained.

Recommended defensive action

Harden authentication and restrict build/script execution to authorized operators.

Attack / finding

Privileged service context

The notes describe high integrity, administrative membership and disabled UAC.

Recommended defensive action

Reduce build account privileges; review unnecessary administrative membership and disabled UAC.

Attack / finding

Unquoted service path

WiseBootAssistant was investigated, but the retained evidence does not establish that this path caused the SYSTEM shell.

Recommended defensive action

Quote the executable path and audit directory write permissions and service control rights.
