sast-triage

I built sast-triage, a GitHub pull request reviewer that scans the changed Python files with Semgrep, labels each finding new or pre-existing, ranks it P1–P3 and fails the check only on new P1 findings.

The problem

A Semgrep step in a repository’s own CI flags every finding, including ones the pull request didn’t introduce, and the pull request can edit that step. sast-triage runs outside the repository with its own rules and separates what a change introduced from what was already there.

Input → scan → output

  1. Authenticate. Verify the webhook’s HMAC-SHA256 signature and validate repository and commit identifiers.
  2. Stage the exact revision. Download a bounded head-commit archive and stage only the changed Python files, scanned whole.
  3. Scan with service-owned rules. Pull request configuration, ignore files and nosemgrep comments cannot disable them.
  4. Report. Post Check Run annotations on the reviewed commit, P1 first, up to 200.

The signature check runs on the exact request body, against every configured secret in constant time, so a secret can be rotated without downtime:

provided = x_hub_signature_256 or ""
if not any(hmac.compare_digest(provided, _hmac_sig(secret, body, "sha256")) for secret in SECRETS):
    raise HTTPException(401, "Invalid signature")

Only a new P1 fails the check. Scanner errors and incomplete scans fail closed. Deleted-only and non-Python changes are neutral. A pass means the scan finished with no new P1 in the scanned files, not that the repository is secure.

Security controls

The webhook sender, repository author and scanner are separate trust boundaries.

  • Archives: reject path traversal, links, duplicates and oversized content.
  • Source: never executed; credentials are kept out of the scanner’s environment.
  • Scanner output: malformed or incomplete results fail the check.

Every archive entry is checked before anything is written. Absolute paths, .., links, special files, a second root or a path that resolves outside the folder stop the scan:

if (name.is_absolute() or ".." in name.parts or not name.parts
        or "\\" in member.name or not (member.isdir() or member.isreg())):
    raise RuntimeError("Unsafe archive member")
if root_name is None:
    root_name = name.parts[0]
if name.parts[0] != root_name or (len(name.parts) == 1 and not member.isdir()):
    raise RuntimeError("Archive must have one root directory")
target = base.joinpath(*name.parts)
if not target.resolve().is_relative_to(base) or target in seen:
    raise RuntimeError("Unsafe or duplicate archive path")

How triage works

Every finding is annotated; two labels decide its priority.

  • New or pre-existing: new when it overlaps a line the pull request added or changed, which is not proof the change caused it. With no readable diff, every finding in the file counts as new. A rename-only file is unchanged, unless it was renamed or copied from test to runtime code; then all its findings count as new.
  • Test or runtime code: pytest and Django naming; conftest.py counts as runtime code.

Low rule confidence or likelihood drops a finding one level; the 15 production rules leave both unset. The whole decision is a few lines of code. A finding is new when any of its lines changed, and an unreadable diff (None) makes every finding new, so a parsing problem can only over-report:

lines = changed.get(f["path"])
new = lines is None or any(n in lines for n in range(f["start_line"], f["end_line"] + 1))
test_code = is_test_path(f["path"])
ranked.append(dict(f, new=new, test_code=test_code,
                   priority=priority(f["severity"], test_code, f.get("confidence"), f.get("likelihood"))))

Priority and the gate:

def priority(severity: str, test_code: bool, confidence: Optional[str] = None,
             likelihood: Optional[str] = None) -> str:
    high = severity in {"CRITICAL", "HIGH"}
    if high and not test_code:
        level = 1
    elif high or (severity == "MEDIUM" and not test_code):
        level = 2
    else:
        level = 3
    if "LOW" in (confidence, likelihood):
        level = min(level + 1, 3)
    return f"P{level}"

def gate(findings: List[Dict[str, Any]]) -> str:
    """The Check Run conclusion: it fails only when a finding is both new and P1."""
    return "failure" if any(f["new"] and f["priority"] == "P1" for f in findings) else "success"

Technologies & stack

  • Service: Python 3.11–3.13, FastAPI, Semgrep, GitHub App webhooks and REST API, PyJWT; opt-in .env loading via python-dotenv.
  • Tests: pytest, HTTPX, Make and GitHub Actions.
  • Prepared deployment: SQLite job queue, separate worker, rootless Docker scanner.
  • Browser demo: HTML, CSS, vanilla JavaScript and JSON fixtures.

Source: application dependencies · deployment scope.

Scope and limits

  • Covers Python with 15 pattern rules: weak hashes, unsafe YAML and pickle loading, shell commands, eval/exec, disabled TLS verification, insecure randomness and temp files, and unsafe tar extraction. They match patterns, not data flow.
  • Pair it with sca-triage for npm dependencies and with other tools for secrets, JavaScript and infrastructure.
  • Findings are review aids; rules can miss issues or report false positives.
  • To use it on your own repository, register your own GitHub App, as the README describes.

Run it yourself

The demo environment has known dependency advisories; use it with the bundled fixtures only.

git clone https://github.com/lansiquo/sast-triage.git
cd sast-triage
python3 -m venv .venv
source .venv/bin/activate
python -m pip install -r requirements.txt
make check

make check runs the 286 offline tests, then the real Semgrep demo shown in the example above.

For the interactive version, run .venv/bin/python demo_web.py and open http://127.0.0.1:8765. Four examples run real Semgrep scans; six run behavioral tests on hash-pinned fixtures against synthetic adapters. The pull request view is simulated.
