PROJECT

sast-triage

I built sast-triage, a GitHub pull request reviewer that scans the changed Python files with Semgrep, labels each finding new or pre-existing, ranks it P1–P3 and fails the check only on new P1 findings. A finding is new only when it overlaps a line the pull request added or changed. That overlap is not proof the pull request created the bug.

The problem

A review needs more than a red or green badge: it needs a location, a reason and an honest statement of coverage. I designed the pipeline so scanner failures cannot become reassuring passes, and files from the repository cannot redefine the scanner’s rules.

Input → scan → output

  1. Authenticate the request. Verify the webhook’s HMAC-SHA256 signature—a shared secret check over the exact request body—then validate the repository and commit identifiers.
  2. Prepare the exact revision. Download a bounded archive of the pull request’s head commit, reject unsafe archive entries and stage only changed Python files. The scan covers each selected file, not just added lines.
  3. Run the service’s own rules. Analyze the staged source with Semgrep. Pull request configuration, ignore files and inline suppression comments cannot disable the production rules.
  4. Return reviewable findings. Convert findings into GitHub Check Run annotations: messages attached to specific files and lines on the reviewed commit. Cap output at 200 annotations, sent in batches of 50.

Outcome handling: only a new P1 finding fails the check. Scanner errors and incomplete scans also fail it, and do not count as a pass. Other findings stay on the check as annotations. Deleted-only and non-Python changes are neutral. A passing result means the scan finished with no new P1 in the scanned Python files—not that the repository is secure.

Security controls

My implementation treats the webhook sender, repository author and scanner as separate trust boundaries: each can supply input the next component must validate.

  • Untrusted archives: reject path traversal, links, duplicate entries and excessive size/member counts before staging source.
  • Untrusted source: never execute repository code, install hooks or tests. Keep application credentials out of the scanner subprocess environment.
  • Scanner failures: reject malformed output and incomplete scans rather than reporting success.

These controls reduce exposure, but staging files and removing credentials don’t create an operating system sandbox. Locally, scans run as ordinary subprocesses; real container isolation is one of the live acceptance checks below.

Technologies & stack

The application is a Python webhook service.

  • Language & API: Python 3.11–3.13, FastAPI and Uvicorn; Pydantic for the API framework's data layer.
  • Security analysis: Semgrep with service-owned Python rules, subprocess execution and JSON findings mapped to GitHub Check Run annotations.
  • GitHub integration & authentication: GitHub App webhooks and REST API; HMAC-SHA256 signature validation; Requests and certifi for HTTPS; PyJWT and cryptography for App authentication; python-dotenv for opt-in local .env loading (make serve turns it on).
  • Tests & developer workflow: pytest, HTTPX, pip, Python virtual environments, Make and GitHub Actions, which runs make check on every pull request and push to main. The local interactive showcase uses FastAPI with HTML, CSS and JavaScript.
  • Prepared durable deployment: SQLite job queue, a separate Python worker and rootless Docker scanner isolation on Linux.
  • This website & browser demo: HTML, CSS, vanilla JavaScript and JSON fixtures, hosted on GitHub Pages.

How triage works

Each finding gets two labels. The check fails only for a new P1. Every finding is still reported on its line.

  • New or pre-existing: a finding is new when any of its lines overlap a line the pull request added or changed. That overlap is not proof the pull request created the bug. A match on an untouched line stays pre-existing, even when another edit, such as a new import, makes that line match. If the diff is missing or can’t be read, every finding in that file counts as new, so a parsing problem can’t hide one. A file that was only renamed, with no edited lines, counts as unchanged—unless it moved from test code to runtime code, in which case every finding in it counts as new, because its priority just went up.
  • Test or runtime code: test code follows pytest and Django naming—a test or tests folder, test_*.py, *_test.py or tests.py. conftest.py counts as runtime code wherever it sits, because pytest imports it on every run.
  • P1: high or critical, in runtime code.
  • P2: high or critical in test code, or medium in runtime code.
  • P3: the remaining findings.

A rule that rates its own confidence or likelihood as low drops one level; the 15 production rules leave both unset, so they rank by severity alone. The check fails only when a finding is both new and P1, and scanner errors or incomplete scans still fail it. Findings on lines the pull request did not add or change stay visible and do not fail the check.

Source: labelling, ranking and the gate.

Scope and limits

  • Covers Python source with 15 service-owned rules for high-signal patterns: weak hashes, unsafe YAML and pickle loading, shell commands, eval/exec, disabled TLS verification, insecure randomness and temp files, and unsafe tar extraction. Pair it with sca-triage for npm dependencies and with dedicated tools for secrets, JavaScript and infrastructure. The rules match risky code patterns rather than tracing data flow between functions.
  • Findings are ranked P1–P3 and labelled new or pre-existing, but a person still reviews them; the rules can miss vulnerabilities or report false positives.
  • To use it on your own repository, run the service and register your own GitHub App, as the README describes.

Run it yourself

The source is on GitHub, and setup uses Python 3.11–3.13. The demo environment has known dependency findings, so use it with the bundled trusted fixtures only, not for public repositories or production.

git clone https://github.com/lansiquo/sast-triage.git
cd sast-triage
python3 -m venv .venv
source .venv/bin/activate
python -m pip install -r requirements.txt
make check

make test runs the offline regression suite with outbound HTTP blocked. make demo runs Semgrep on three bundled fixtures, without executing those files, and prints the triage and annotation JSON. make check runs both.

This local scan is separate from the curated browser demo. It treats vulnerable.py and test_reports.py as one pull request, then scans clean.py alone. Five findings are checked on that pull request, and only one fails the gate. shell=True is high severity in runtime code, on a line the diff adds, so it is a new P1. MD5 is the same severity in that file, on an unchanged line, so it is a pre-existing P1. pickle.loads is high severity in the test file, on an added line, so it is a new P2. random used for a token is medium severity in runtime code, on an added line, so it is a new P2. tempfile.mktemp is medium severity in the test file, on an unchanged line, so it is a pre-existing P3. clean.py uses sha256, which these rules do not match, and the demo checks that this scan passes with no findings.

For the full interactive version, run .venv/bin/python demo_web.py and open http://127.0.0.1:8765. It’s the local counterpart of the browser demo: pick an example, run the check, apply the fix and run it again. Four examples run real Semgrep scans with a small demo ruleset; six run real behavioral tests that execute authored, hash-pinned fixtures in bounded child processes against synthetic adapters. The pull request view is simulated, and only bundled fixtures are accepted.
