sast-triage

I built sast-triage, a Semgrep reviewer for Python, JavaScript and TypeScript that labels each finding new or pre-existing, ranks it P1–P3 and fails only on new P1 findings. Here it runs on OWASP NodeGoat, a deliberately vulnerable Express app.

The problem

A Semgrep step in a repository’s own CI reports every finding with the same urgency, including ones the pull request didn’t introduce, and the pull request can edit that step. sast-triage uses its own rules and separates what a change introduced from what was already there.

OWASP NodeGoat is a deliberately vulnerable Express and MongoDB app for learning the OWASP Top 10. At its latest commit (c5cb68a, June 2023) the rules find 10 issues in its 44 source files, 7 of them P1. Its last two pull requests introduced none of them.

Ten findings cover five of NodeGoat’s lessons and its server-side request forgery. It misses the rest: log injection, plain-text passwords, insecure direct object references, missing security headers, plain HTTP, missing access control, CSRF and a ReDoS-prone regex. No rule covers those, HTML templates aren’t scanned, and data isn’t traced across files. Vulnerable dependencies (A9) are sca-triage’s job.

How it works

Ranking combines rule severity with where the code lives:

  • P1: high or critical, in runtime code.
  • P2: high or critical in test code, or medium in runtime code.
  • P3: everything else.

A finding is new when it covers a line the pull request added or changed, or when the file didn’t have it before the change: for files with a finding on an untouched line, the version before the pull request is scanned too, so editing one line can’t make another dangerous unnoticed. Only a new P1 fails the gate. An unreadable diff makes every finding new, and scanner errors or incomplete scans fail the gate, so a problem can over-report but never pass silently.

The 41 rules (21 Python, 20 JavaScript and TypeScript) belong to the tool. Eight follow request data from Flask, Django and Express into SQL queries, file paths, outgoing requests and HTML responses. The scanned repository’s Semgrep configuration and nosemgrep comments can’t switch them off, and Semgrep never downloads rules. The GitHub App verifies each webhook’s HMAC-SHA256 signature, downloads only the changed files, and reports results as Check Run annotations, P1 first.

Built with Python and Semgrep, it runs as a CLI, a GitHub Action or a FastAPI GitHub App. Source: labelling, ranking and the gate · scanner checks · rules · architecture.

What has been verified

Checked on sast-triage v2.1.1 (9b5e308): make check passed all 197 tests and the self-check, and the NodeGoat runs above were made with the same scanner code.

197 offline tests
Run with outbound HTTP blocked and GitHub and Docker calls mocked, covering diff labelling, the comparison with the code before a change, ranking, the gate, the scanner checks, the webhook and the durable queue.
CI
make check on Python 3.11–3.14, plus a run of the GitHub Action that must fail on a planted P1, on every push to main and every pull request.
41 service-owned rules
Each has positive and negative tests, and all pass the scanner validation, including suppression resistance. On OWASP Juice Shop the new rules find its SQL injections in login.ts and search.ts and its request forgery.
A real project
OWASP NodeGoat, scanned whole and by pull request with the output above, so anyone can repeat the run. All 78 of its merged pull requests were also scanned as pull requests.

Scope and limits

  • Covers Python, JavaScript and TypeScript with 41 rules. Request data is followed within one function, so a value passed through another function or module before a dangerous call isn’t traced.
  • New is judged file by file: only changed files are scanned, so a change in one file that makes code in another dangerous isn’t caught.
  • The GitHub App’s live deployment (Linux image audit, rootless container boundaries and authenticated GitHub delivery) is prepared but not complete.
  • HTML templates aren’t scanned. Pair it with sca-triage for npm dependencies and with other tools for secrets and infrastructure.

Run it yourself

Requires Python 3.11–3.14. From an empty folder:

git clone https://github.com/lansiquo/sast-triage.git
python3 -m venv sast-venv
sast-venv/bin/pip install -r sast-triage/requirements-cli.txt
git clone https://github.com/OWASP/NodeGoat.git
sast-venv/bin/python sast-triage/scan_repo.py NodeGoat
sast-venv/bin/python sast-triage/scan_repo.py NodeGoat --base HEAD~2

Both scans only parse files and run none of NodeGoat’s code. The whole-project scan exits with code 1 because the P1 gate fails; the pull request scan exits with 0. To gate your own pull requests, add the GitHub Action to a workflow that runs on pull_request:

- uses: actions/checkout@v4
  with:
    fetch-depth: 0
- uses: lansiquo/sast-triage@v2.4.0

The Action’s optional timeout input is the scanner time limit in seconds: timeout: 600 gives a large scan twice the default 300 seconds. Its optional sarif input, empty by default, names a file to also write the findings to as SARIF 2.1.0 for GitHub code scanning, as scan_repo.py --sarif FILE does on the command line. The Action doesn’t upload the file and sast-triage itself uses no token: uploading is a separate step of your own workflow.
